Crate scope audit — bupha under ADR-0006 ​

Per-crate ruling for every crate in crates/, against ADR-0006 ("bupha is CI semantics only — substrate is hypha/peregrin, distribution is tamias") and the P-002 ci-job ops contract.

Rulings:

  • KEEP — CI semantics or runner/dialect/forge/status knowledge that stays in bupha.
  • MIGRATE — stateful/infra machinery that becomes a hypha-side impl or dies in favor of ci-job entities. Target home noted.
  • DIE — fully subsumed, no port value.
  • SPLIT — crate mixes semantics + machinery; noted per half.
  • DEV — survives only as the in-process dev/test harness (ADR-0006: "ports stay, impls get swapped").

Incoming ​

  • bupha-plane (new, P-002) — KEEP. Thin hypha_http::EntityPlane adapter holding ci-job entity state and dispatching ci.* ops; the pure transition math stays in bupha-core. First bupha→hypha dep — confirm acceptable (P-002 open question 1).

Key judgment calls ​

  • Queue family: the semantics (Queue, supersede/retry math, MAX_PENDING) stay in bupha-core as the spec the plane mirrors; the port + in-process impl (bupha-queue) stay for dev/test per P-002; the distributed impls (-redb, -redis) and the lease port migrate/die — fencing becomes entity state (fence + leaseExpiresAt + op CAS), not a separate port.
  • Cache: bupha-cache/-sccache are KEEP — they render runner conf, they don't are a cache. The substrate cache concern (worktree/build artifacts across nodes) is hypha's and was never these crates' job.
  • Ingress trio (webhook/trigger/sturn): normalization (Trigger, Push, Verdict, sturn WAL→push) is KEEP — it's the "forge event → job spec" half of ADR-0006. Listener harnesses are dev-mode; production ingress is peregrin's.
  • Secrets trio (secret/keyring/dotenv): judged generic infra, not CI semantics — but the ruling is gated on T-056 (cuora vs env vs keyring). hypha already ships hypha-{secret,keyring,dotenv} impls, so MIGRATE has a ready home; under cuora they all DIE.
  • Service/lifecycle (service/systemd/tunnel/cloudflared): all generic host machinery — tamias (deploy/provider) + hypha (service/systemd) own it now. DIE or MIGRATE; nothing here is CI semantics.
  • Enterprise surfaces (access*/attest*/audit-file/history/ telemetry*): KEEP as optional bupha features — they encode CI-specific policy (who may trigger, run provenance, audit trail), not generic substrate. Only history is a maybe-fold into the entity index later.
  • bupha-cli: SPLIT — dev harness survives, user-facing binary dies per the ADR-0006 amendment; tamias-driver-bupha worker is the production worker host.

Open questions ​

  1. Secrets story (T-056) gates bupha-secret/-keyring/-dotenv: cuora → all three die; env/keyring → port stays thin, impls duplicate hypha's. Pick before migrating.
  2. bupha-queue-redb: migrate the redb code hypha-side as a local durable queue impl, or let the entity plane cover single-box too (dev uses MemWorkQueue) and DIE it? Lean: DIE unless hypha wants a non-entity queue.
  3. bupha-plane home (P-002 Q1): bupha crate dep'ing on hypha-http vs plane code inside peregrin-node. Audit assumes the bupha crate.
  4. history/audit-file vs entity index: do ci-job entities + ci.status fully replace history.jsonl/audit.log in hosted mode, making both dev-only? Probably yes; confirm before deleting read paths the driver still uses.
  5. bupha-telemetry-otel vs hypha-telemetry: keep the OpenMetrics textfile impl in bupha, or does hypha-telemetry absorb textfile export? Different export shapes today — keep for now.
  6. Tunnel: does hypha/peregrin want a generic tunnel port at all, or is ingress exposure always a campaign/deploy concern (named tunnel via tamias)? Determines whether bupha-tunnel's trait migrates or just dies.

Resolution — T-077 (landed) ​

With T-055 (ADR-0007: ingress is peregrin-owned, bupha webhook surfaces are standalone/dev mode) and T-056 (cuora canonical, T-059 migration verified) done, the remaining MIGRATE/DIE crates were retired in three commits on main:

CrateOutcome
bupha-secretDIE — trait identical to hypha_secret::Secrets; consumers take the hypha git dep directly.
bupha-keyringDIE → hypha-keyring with service = "bupha" so pre-cuora keyring entries still resolve.
bupha-dotenvDIE → hypha-dotenv — ~/.config/bupha/env path/format unchanged.
bupha-secret-cuoraKEEP — the canonical store; now implements hypha_secret::Secrets (already wrapped hypha-secret-cuora).
bupha-serviceDIE — one impl (bupha-systemd), consumers used free fns/struct, not the trait.
bupha-systemdDIE → hypha-systemd — unit render/control via write_unit/enable/disable/status/restart/unit_path/default_unit_dir. Bupha-shaped helpers (write_env_skeleton, service_logs, strict daemon-reload on destroy, SystemdService wrapper) folded into bupha-cli's deploy module. Unit diffs: bare name + .service suffix, quoted ExecStart argv, EnvironmentFile=-, Restart=on-failure.
bupha-tunnel + bupha-cloudflaredFOLDED → bupha-watch::tunnel — ADR-0007 keeps them as the standalone/dev-mode ingress; no hypha tunnel impl exists or is wanted (ingress exposure is a deploy/campaign concern).
bupha-webhookFOLDED → bupha-watch::webhook — same reasoning; tiny_http dep moved to bupha-watch.

Open questions 1 and 6 are thereby resolved: cuora won the secrets story (legacy keyring/dotenv legs survive only as hypha-backed fallbacks in the dev chain), and no generic tunnel port migrates — the trait lives on inside bupha-watch for standalone mode only.
