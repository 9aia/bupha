Architecture ​

Binary surface (ADR-0006 amendment). bupha's shipped surface is the engine library plus tamias-driver-bupha — tamias bundles (type: bupha) deploy provider units that exec the driver's host verb, which runs the watcher engine (bupha-watch) in-process. The bupha CLI binary is a dev/debug harness (run/doctor/import/watch); production webhook ingress is a peregrin campaign (ADR-0007), with the bupha webhook listener as the standalone/dev fallback.

bupha is a port/adapter monorepo: every external concern sits behind a trait (a port), and each integration is a crate that implements it (an impl). bupha-core is the pure domain — config shape, queue semantics, shared primitives — and depends on nothing outside itself; bupha-cli is the engine lib + clap tree (command()/run_from) the dev harness and the driver's cli/ ops surfaces share (the deployed composition is tamias-driver-bupha + tamias provider units).

Sources — the ingest edge ​

bupha is a queue engine: source → queue → effect. Everything in front of the queue is a Source — a long-running ingest that emits normalized (repo, ref, sha, sender) pushes; everything behind it (queues, runner, status sinks) is source-agnostic. A watcher process — tamias-driver-bupha host in deployed units, bupha watch in the dev harness — runs every configured source and feeds one shared ingest path.

sourceconfigemits on
github-webhooktrigger.kind = "github" (+ [trigger] listener, secrets, tunnel)verified push/pull_request deliveries ([[repo]] events)
sturn-wal[trigger.sturn] + [[repo]] sturn = trueOp::Snapshot WAL events

pull_request deliveries are opt-in per repo (events): the PR head sha runs in a worktree while branch/job filters evaluate the base ref — a refs/heads/main gate covers PRs targeting main with no extra config.

Trigger is the narrower per-request port a webhook Source drives — is this our event, which repo (untrusted hint), does the signature verify, what does the payload ask for. New forges mean a new Trigger impl reusing the same webhook listener; new kinds of ingest (gitlab webhook, cron, poll-ref, file-watch) are new Source impls — neither touches the queue.

Webhook request flow ​

The github-webhook source's per-request pipeline (byte-stable — routing and statuses are part of the contract):

POST /hook
  → 1. path check (404 otherwise)
  → 2. read body (≤ 2 MiB)
  → 3. repo hint — untrusted peek at repository.full_name,
       selects the watched [[repo]] and its secret; an
       unwatched repo 404s (it can never verify)
  → 4. signature verify (Trigger port — github impl: HMAC
       sha256, constant-time; key = repo's secret_env,
       falling back to trigger.secret_env)
  → 5. dedup delivery id (bounded 10k ring; github impl uses
       X-GitHub-Delivery)
  → 6. parse — skip deletes/zero-sha; revision must be path-safe
  → 7. route — git_ref selects every job of the repo watching it
       ([[repo.jobs]] entries, or the repo's implicit pipeline);
       forge-attested sender checked against the access policy
  → 8. enqueue — one queue per job; a push fan-outs into every
       matched queue; jobs this box's `[worker] labels` can't
       satisfy belong to the ci-job entity plane instead; persist
       via QueueStore (dev `json` file)
  → 9. one global worker — Vcs fetch, detached worktree
       at <base>-<repo>[-<job>]-<sha12>
  → 10. spawn run handle (token via env:// name, never argv)
  → 11. status — pending → success/error; superseded and
        cancelled shas get honest error statuses. Runners may
        report sub-job verdicts (`Runner::status_reports`) —
        the gha dialect emits one per expanded workflow job /
        matrix leg, posted under `<context>/<workflow>/<job>`
        via `StatusSink::post_ctx` before the aggregate lands

Queue semantics ​

Queues are per job: a [[repo]] is one implicit pipeline unless it declares [[repo.jobs]], in which case each job gets an independent queue (name:job keys), branch filter, runner and status context. One push fan-outs into every job queue whose branch matches the ref — same-repo jobs are independent of each other (latest-wins on one never touches another's pending slot, and cancel_running only kills its own job's in-flight run).

policypendingon new pushuse for
latest (default)1 shasupersedes pending; cancel_running may kill in-flightCI gates
allbounded FIFO (32)appends; oldest evicted past cap; cancel_running rejected at load — it would drop a promised commitreleases

Persistence: accepted work writes through the QueueStore port (the dev json file under worktree.base; the durable path is the ci-job entity plane — see distributed runners) and on restart the interrupted running sha is re-queued at the front.

One global worker serializes runs across all repos — a second push queues behind the in-flight job. Deliberate (one box, bounded resource use), not a hang: journalctl --user -u bupha-watch shows the queue moving.

Security model ​

  • mandatory HMAC (constant-time compare) — unauthenticated payloads never reach the queue
  • per-repo webhook secrets ([[repo]] secret_env, falling back to trigger.secret_env) — the repo is resolved before verify, so a hook admin on one repo can't forge signed pushes for another
  • body cap, delivery-id replay dedup, hex-sha validation before the value touches paths or status URLs
  • webhook takeover is exact-URL only; hook API calls are timed out
  • config names secrets (secret_env/token_env) — values resolve env → cuora (cuora://bupha/<NAME>, canonical, T-056; fleet secrets migrated, T-059) → ~/.config/bupha/env (0600 — dev-mode / no-cuora fallback; keyring leg dropped post-T-077); the runner gets the token through its own mechanism (env:// for dagger)

Where it sits ​

Bupha is the CI gate — the delivery layer's event-driven job runner, shipped as tamias content:

delivery  →  memory  →  process  →  interface
tamias,      myco,       sturn,      pavo views,
scarab,      kuda,       cuora,      bupha dev
tarsi,                 mimus,       CLI shim
bupha ◄──              cicada,
hypha                  lasius,
                        sepia,
                        peregrin

A type: bupha bundle installs through tamias like any other pack; the provider unit runs tamias-driver-bupha host/worker which embed this organism. Durable fleet state lives on the hypha entity plane (ci-job entities) — the substrate peregrin campaigns orchestrate on — bupha owns the semantics (queue policies, worktree isolation, runner dialects, forge statuses), the plane owns the state.

See Boundaries for owns / does-not-own.
